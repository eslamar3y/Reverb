01

What is Laravel Reverb?ما هو Laravel Reverb؟

Reverb is Laravel's first-party WebSocket server. It gives a Laravel application a persistent, bidirectional connection to clients, while fitting directly into Laravel's existing event broadcasting system.

Reverb هو خادم WebSocket الرسمي من Laravel. يوفّر اتصالًا دائمًا وثنائي الاتجاه بين تطبيق Laravel والعملاء، ويتكامل مباشرةً مع نظام Event Broadcasting في Laravel.

Why it exists

Traditional HTTP is request/response: the browser asks and the server answers. Reverb adds a long-lived connection so the server can push an event as soon as something changes.

First-party integration

Reverb works with Laravel Broadcasting and Laravel Echo. It uses the Pusher protocol, which is why the Echo client can communicate with Reverb using the Reverb broadcaster.

Open source + self-hostable

You run the WebSocket process alongside your Laravel application. This gives you direct control over networking, resources, security, and deployment.

What Reverb is not

Reverb is not Laravel Echo. Echo is a JavaScript client library; Reverb is the server that maintains WebSocket connections and distributes broadcast messages.

Core mental model: Laravel decides what happened and where it should be broadcast. Reverb maintains the WebSocket connections. Echo consumes the event in the browser.Laravel يحدد ماذا حدث وأين يتم بثه. Reverb يدير اتصالات WebSocket، وEcho يستقبل الحدث داخل المتصفح.
02

Real-time communication explainedشرح الاتصال اللحظي

Real-time does not mean “zero latency”. It means the application can deliver changes without requiring the user to repeatedly refresh or request the same state.

الاتصال اللحظي لا يعني تأخيرًا يساوي صفرًا؛ المقصود أن التطبيق يستطيع إيصال التغييرات بدون أن يضطر المستخدم لعمل Refresh أو إرسال طلبات متكررة لنفس الحالة.

HTTP request / response

Client sends a request → server processes it → server returns a response → connection ends. Excellent for APIs and page navigation, but the server cannot spontaneously push a new event over that completed request.

Polling

The client repeats HTTP requests every N seconds. Simple, but it creates requests even when nothing changed and introduces a polling interval as an upper bound on freshness.

Long polling

The server holds an HTTP request until data is available or a timeout occurs. It can reduce empty responses, but the client still reconnects repeatedly.

Server-Sent Events

SSE keeps an HTTP connection open for server → client streams. It is useful for one-way updates, but it is not a bidirectional WebSocket channel.

WebSockets

A persistent connection starts as HTTP and upgrades to WebSocket. Both client and server can send messages over the same connection, making it suitable for chats, status updates, dashboards, and collaboration.

Why Reverb?

It gives Laravel a dedicated WebSocket server while preserving Laravel's event/channel abstractions. Your application code can remain event-driven rather than manually managing socket connections.

How Laravel Reverb worksكيف يعمل Laravel Reverb

Think in layers. Laravel's application layer remains responsible for business logic; Broadcasting describes the delivery contract; Reverb handles persistent WebSocket connections; Echo translates those broadcasts into frontend callbacks.

فكّر في النظام كطبقات: Laravel مسؤول عن Business Logic، وBroadcasting يحدد عقد التوصيل، وReverb يدير اتصالات WebSocket، وEcho يحوّل الأحداث إلى callbacks في الواجهة.

Laravel Application
→
Laravel Broadcasting
→
Reverb Server
→
Connected Clients

1. Laravel Application

Your controller, service, job, model observer, or domain logic changes application state and dispatches an event.

2. Broadcasting

An event implementing ShouldBroadcast tells Laravel that this event should be delivered through the configured broadcasting driver. Broadcasting is normally queued.

3. Reverb

The long-running Reverb process accepts WebSocket connections, keeps track of subscriptions, and distributes broadcast messages to matching connected clients.

4. Client

Laravel Echo subscribes to a channel and listens for the event. Your UI then updates local state, a badge, a table row, a map marker, or another component.

Installationالتثبيت

For current Laravel applications, Laravel documents a one-command broadcasting setup with --reverb. Manual installation is also supported and is useful when you want to understand each package and configuration step.

في إصدارات Laravel الحالية، يوجد أمر واحد لتجهيز Broadcasting مع Reverb باستخدام --reverb، كما أن التثبيت اليدوي متاح لفهم كل package وconfiguration خطوة بخطوة.

bash
# Recommended integrated setup

# Manual setup
composer require laravel/reverb

npm run build

Enables broadcasting, installs the Reverb server package and frontend scaffolding required by the selected setup, and updates environment/configuration.

Publishes Reverb configuration, adds the required environment variables, and enables broadcasting for Reverb when using the manual path.

Version note: Laravel's current documentation requires the Echo Reverb broadcaster support available in modern Echo releases; check your project's Laravel/Echo/Reverb versions when copying examples across major versions.ملاحظة الإصدارات: تأكد من توافق إصدارات Laravel وEcho وReverb عند نقل الأمثلة بين مشاريع بإصدارات Major مختلفة.

Configurationالإعدادات Configuration

.env
REVERB_APP_ID=your-app-id
REVERB_APP_KEY=your-app-key
REVERB_APP_SECRET=your-app-secret

# Public address used by the broadcasting side

REVERB_PORT=443

REVERB_APP_ID

Identifies the Reverb application configuration. Treat application credentials as server configuration, not user data.

REVERB_APP_KEY

The public application key used by the client-side connection configuration.

REVERB_APP_SECRET

Server-side application secret used for authentication/signing. Never expose it in frontend code.

REVERB_HOST / PORT / SCHEME

Describe the address Laravel uses to send broadcast messages to the Reverb server. In production this can be a public hostname on 443 while Reverb itself listens on 8080.

REVERB_SERVER_HOST / PORT

Describe where the Reverb process itself binds. Do not confuse these with the public/broadcast destination variables.

Allowed origins

Reverb's config/reverb.php supports application-level allowed origins. Restrict origins in production instead of using * unless that is genuinely required.

07

Broadcasting eventsBroadcasting وLaravel Events

Broadcasting is the Laravel abstraction. Your event describes its channels and payload; Laravel's configured broadcasting driver delivers it. Broadcast events are normally queued, so a queue worker is part of the production architecture.

Broadcasting هو الـ abstraction داخل Laravel. الـ Event يحدد القنوات والبيانات، والـ driver المكوّن يقوم بالتوصيل. أحداث الـ Broadcasting تكون عادةً queued، لذلك Queue Worker جزء من الـ production architecture.

php · app/Events/OrderCreated.php
<?php

namespace App\Events;

use App\Models\Order;
use Illuminate\Broadcasting\Channel;
use Illuminate\Broadcasting\PrivateChannel;
use Illuminate\Contracts\Broadcasting\ShouldBroadcast;
use Illuminate\Queue\SerializesModels;

class OrderCreated implements ShouldBroadcast
{
    use SerializesModels;

    public function __construct(
        public Order $order,
    ) {}

    /**
     * The channel(s) that receive this event.
     */
    public function broadcastOn(): array
    {
        return [
            new PrivateChannel('orders.' . $this->order->id),
        ];
    }
}

ShouldBroadcast

Marks the event for broadcasting. Laravel sends it through the configured broadcasting driver.

broadcastOn()

Returns a Channel, PrivateChannel, PresenceChannel, or an array of channels.

Public channel

new Channel('orders'). No authentication/authorization is required to subscribe to a public channel.

Private channel

new PrivateChannel('orders.'.$id). Laravel authorizes the subscriber through the broadcasting auth flow.

php · routes/channels.php
<?php

use App\Models\User;
use Illuminate\Support\Facades\Broadcast;

Broadcast::channel('orders.{order}', function (User $user, int $order) {
    // Replace with your real ownership / permission rule.
    return $user->orders()->whereKey($order)->exists();
});

Laravel EchoLaravel Echo

Echo is the client-side JavaScript library that subscribes to channels and listens for events. With Reverb, Echo uses the reverb broadcaster and Reverb's Pusher-compatible protocol.

Echo هي مكتبة JavaScript في الـ frontend للاشتراك في القنوات والاستماع للأحداث. مع Reverb تستخدم Echo الـ reverb broadcaster وبروتوكول Reverb المتوافق مع Pusher.

javascript
import Echo from 'laravel-echo';
import Pusher from 'pusher-js';

window.Pusher = Pusher;

window.Echo = new Echo({
    broadcaster: 'reverb',
    key: import.meta.env.VITE_REVERB_APP_KEY,
    wsHost: import.meta.env.VITE_REVERB_HOST,
    wsPort: import.meta.env.VITE_REVERB_PORT ?? 80,
    wssPort: import.meta.env.VITE_REVERB_PORT ?? 443,
    forceTLS: (import.meta.env.VITE_REVERB_SCHEME ?? 'https') === 'https',
    enabledTransports: ['ws', 'wss'],
});
Browser variables: Values consumed by Vite frontend code must use the VITE_ prefix. Never put REVERB_APP_SECRET into client-side variables.القيم التي يقرأها Vite في الـ frontend يجب أن تبدأ بـ VITE_. لا تضع REVERB_APP_SECRET في كود المتصفح.

Listening for eventsالاستماع للأحداث

javascript
// Public channel
Echo.channel('orders')
    .listen('OrderCreated', (event) => {
        console.log(event);
    });

// Private channel
Echo.private(`orders.${orderId}`)
    .listen('OrderCreated', (event) => {
        updateOrder(event.order);
    });

// Presence channel
Echo.join(`team.${teamId}`)
    .here((users) => console.log('Online:', users))
    .joining((user) => console.log('Joined:', user))
    .leaving((user) => console.log('Left:', user))
    .listen('TaskUpdated', (event) => {
        refreshTask(event.task);
    });

private()

join()

// Leave a channel

Presence channelsPresence Channels

Presence channels build on private-channel security and add awareness of who is currently subscribed. They are useful when membership itself is part of the feature.

Presence Channels تبني على أمان Private Channels وتضيف معرفة المستخدمين المشتركين حاليًا. تستخدم عندما تكون معرفة أعضاء القناة جزءًا من الـ feature نفسها.

Online users

Show who is currently active in a room, dashboard, or project.

Collaboration

Show “X is viewing this page” or active teammates.

Chat rooms

Track membership while broadcasting messages to the room.

php
Broadcast::channel('chat.{room}', function (User $user, int $room) {
    if (! $user->can('viewChatRoom', $room)) {
        return false;
    }

    // Returned data is exposed to presence listeners.
    return ['id' => $user->id, 'name' => $user->name];
});
javascript
Echo.join(`chat.${roomId}`)
    .here((users) => renderOnlineUsers(users))
    .joining((user) => addUser(user))
    .leaving((user) => removeUser(user))
    .listen('NewMessage', (event) => appendMessage(event.message));

Reverb vs pollingReverb مقابل Polling

Polling

Client → Server
Client → Server
Client → Server
Client → Server

The client decides when to ask. If nothing changed, the request still consumed network and server resources.

WebSocket

Client ←→ Server

The connection persists. Once subscribed, the server can send an event when the underlying application state changes.

Do not eliminate polling everywhere: Polling is often simpler and perfectly adequate for low-frequency data. Use WebSockets when the value of immediacy justifies the operational complexity.لا تلغِ Polling في كل مكان: أحيانًا يكون أبسط ومناسبًا جدًا للبيانات قليلة التغيّر. استخدم WebSockets عندما تكون فائدة التحديث الفوري تستحق التعقيد التشغيلي.

Scaling Reverbتوسعة Reverb

A WebSocket server is a long-running process. Scaling is not just “add another PHP worker”: clients are connected to specific Reverb processes, so the system needs a strategy for distributing connections and propagating broadcasts between nodes.

خادم WebSocket عملية طويلة التشغيل. الـ Scaling ليس مجرد إضافة PHP worker؛ العميل يكون متصلًا بعملية Reverb محددة، لذلك تحتاج لتوزيع الاتصالات ونشر الـ broadcasts بين الـ nodes.

Horizontal scaling

Run multiple Reverb servers behind a load balancer. Each server owns its connected sockets.

Redis Pub/Sub

Reverb can use Redis publish/subscribe so a broadcast received by one Reverb server can reach connections held by other Reverb servers.

Queues

Broadcast events are normally queued. Queue workers are separate from the long-running Reverb process and must be monitored independently.

Server resources

Each connection consumes resources. File descriptor limits, memory, CPU, network throughput, event-loop performance, and proxy timeouts all matter.

.env
# Enable Reverb's horizontal scaling support
REVERB_SCALING_ENABLED=true
Load Balancer
→

↔
Redis Pub/Sub
↔

For multiple nodes, use a central Redis instance accessible by all Reverb servers and put the Reverb nodes behind a load balancer. Your deployment must also account for WebSocket connection timeouts and, where required by your load-balancer architecture, connection affinity.

عند استخدام أكثر من node، استخدم Redis مركزيًا يمكن لكل Reverb server الوصول إليه، وضع الـ nodes خلف Load Balancer. ويجب ضبط WebSocket timeouts وأي connection affinity تحتاجها البنية المستخدمة.

Production deploymentالنشر في Production

bash
# Start Reverb
php artisan reverb:start

# Debug the stream while diagnosing a problem
php artisan reverb:start --debug

# Gracefully restart the long-running server
php artisan reverb:restart

# Run Laravel's queue worker separately
php artisan queue:work

Process supervision

Run Reverb under Supervisor, systemd, or an equivalent process manager so it restarts after failure and survives deployments.

Reverse proxy

In common production setups, Nginx or another web server terminates TLS and proxies WebSocket traffic to Reverb on an internal port such as 8080.

SSL / TLS

Expose wss:// to browsers in HTTPS production environments. Make sure the proxy supports HTTP/1.1 upgrade and preserves the required headers.

Monitoring

Monitor Reverb process health, connection counts, memory, CPU, network traffic, queue latency, failed jobs, and proxy errors.

nginx · conceptual
server {
    listen 443 ssl;
    server_name ws.example.com;

    location / {
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;

        # WebSocket upgrade
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "Upgrade";

        proxy_pass http://127.0.0.1:8080;
    }
}
Architecture detail: REVERB_HOST/PORT can represent the public destination while REVERB_SERVER_HOST/PORT represent the process bind address. A public 443 → internal 8080 arrangement is a normal pattern.REVERB_HOST/PORT يمكن أن يمثل العنوان العام، بينما REVERB_SERVER_HOST/PORT يمثل مكان استماع عملية Reverb. مثلًا Public 443 → Internal 8080 نمط طبيعي.

Securityالأمان

01Private channels: use them for user-specific or sensitive events instead of public channels.
02Authorization: make routes/channels.php enforce actual ownership/permission rules.
03Secrets: keep REVERB_APP_SECRET server-side and out of source control/frontend bundles.
04WSS: use TLS in production and proxy WebSocket traffic securely.
05Origins: configure allowed origins in config/reverb.php for your actual client origins.
06Defense in depth: WebSocket authorization does not replace authorization on your REST/API endpoints.

Debuggingاستكشاف الأخطاء

WebSocket connection failed
Check the browser network tab, public hostname, port, TLS certificate, Nginx upgrade headers, firewall/security groups, and whether reverb:start is actually running.
403 / channel authorization error
Verify the authenticated user, the exact channel name, routes/channels.php, the authorization callback, and the authentication/session or token configuration used by your frontend.
Event is never received
Check that the event implements ShouldBroadcast, the channel name matches exactly, the queue worker is running, the event is actually dispatched, and the browser listener uses the correct event name.
Wrong REVERB_HOST / port
Distinguish the public broadcast destination (REVERB_HOST/PORT) from the server bind address (REVERB_SERVER_HOST/PORT). In production they may intentionally differ.
Queue is not running
Broadcasting is normally queued. Inspect failed jobs and queue worker logs; restarting Reverb does not replace a missing queue worker.
HTTPS / WSS problems
Confirm the certificate, browser mixed-content rules, proxy upgrade headers, correct forceTLS behavior, and public port 443 configuration.
CORS / origin problems
Inspect Reverb's allowed origins and the Laravel authentication endpoint. A successful HTTP API call does not automatically mean a WebSocket subscription is authorized.
bash
# Run Reverb with verbose stream output during diagnosis
php artisan reverb:start --debug

# Check queue processing
php artisan queue:work

# Gracefully restart Reverb after configuration/code changes
php artisan reverb:restart

Performance tipsنصائح الأداء

Broadcast only meaningful state changes

Do not emit high-frequency events if the UI does not need every intermediate state.

Keep payloads focused

Broadcast the fields the client needs. Avoid serializing large models or unnecessary relationships.

Use queues correctly

Keep broadcast work out of latency-sensitive HTTP requests and size workers according to workload.

Measure connection capacity

Test realistic concurrent connections and message rates. Capacity depends on your server, PHP/runtime extensions, network, payload size, and workload.

Optimize the reverse proxy

Use appropriate keepalive and read/send timeouts and ensure WebSocket upgrades are handled correctly.

Scale with evidence

Move to multiple Reverb nodes when measured connection/resource limits require it, not merely because the application has WebSockets.

Common mistakesأخطاء شائعة

Confusing Echo with Reverb

Echo is the client. Reverb is the WebSocket server.

Using public channels for sensitive data

Use private/presence channels and authorization rules where access is restricted.

Forgetting the queue worker

The event can be dispatched successfully while the broadcast job remains unprocessed.

Mixing public and server ports

REVERB_PORT and REVERB_SERVER_PORT can have different values in reverse-proxy deployments.

Expecting code changes to hot-reload Reverb

Reverb is long-running. Use reverb:restart or let your process manager restart it during deployment.

Broadcasting giant payloads

Realtime does not mean “send the whole model”. Keep events small and intentional.

FAQالأسئلة الشائعة

Is Reverb the same as Laravel Echo?
No. Reverb is the server-side WebSocket server. Echo is the client-side JavaScript library that subscribes to channels and listens for broadcasts.
Do I need a WebSocket server if I already have Laravel?
Laravel's normal PHP request lifecycle does not maintain browser WebSocket connections. Reverb supplies that long-running WebSocket process.
Do broadcasts require queues?
Laravel documents event broadcasting as queued by default. Run and monitor an appropriate queue worker in environments where your broadcasts are queued.
Can I use private channels with Reverb?
Yes. Private and presence channels are part of Laravel Broadcasting. Laravel authorizes private subscriptions through the broadcasting authentication flow.
Can Reverb scale across multiple servers?
Yes. Laravel's Reverb documentation describes horizontal scaling through Redis publish/subscribe and multiple Reverb servers behind a load balancer.
Should every realtime feature use WebSockets?
No. Choose the communication model based on freshness requirements, event frequency, operational complexity, and expected load. Polling can be perfectly reasonable for low-frequency state.
Why does Reverb use the Pusher protocol?
Reverb implements the Pusher protocol for WebSockets, which enables compatibility with the Laravel Echo/Reverb broadcasting path and the pusher-js package used by manual Echo configuration.

Consider Reverb when your Laravel product benefits from server-initiated updates: notifications, chat, operational dashboards, order/delivery state, collaborative interfaces, or other event-driven UI. Start with a clear channel model, small payloads, correct authorization, a healthy queue, and a measurable production deployment. Scale the WebSocket layer only as your connection and traffic profile demands it.
